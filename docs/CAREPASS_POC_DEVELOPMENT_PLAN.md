# 照護通 CarePass：POC 完整開發流程

規劃日期：2026-11-07，Asia/Taipei。對應 [修正版 POC 規格](CAREPASS_POC_SPEC.md)。

本文件保留預計的完整開發流程。CarePass 前端與城市通入口已開始實作；Flutter 與網站已拆成獨立 repository，App 必須載入網站部署後的 HTTPS 網址。實際啟動方式、測試結果與未驗證事項見 `../carepass/README.md`。

## 1. 排程假設與人力

- 既有 TownPass 專案能在至少一台目標手機成功建置；尚未由本次工作實測。
- 技術採既有 Flutter App 加 React／TypeScript 靜態微服務；不建立使用者帳號、雲端個人資料庫或即時預約後端。
- 預估 P0 為 25–34 人時；兩位熟悉相關技術的開發者並行，搭配一位可兼任內容、介面與測試的協作者，約需 14–18 小時的工作時段。這是估算，包含任務交接，未包含休息、等待訪談或重大建置問題。
- 單人預估 25–34 個工作小時，不能直接套用兩人競賽排程。競賽前以最小 Demo 範圍交付，剩餘驗證據實標記。
- 建議一般排程額外留約 20% 緩衝；若受競賽期限限制，優先刪減功能，再保留整合與展示時間。

| 角色 | 主要責任 |
| --- | --- |
| 開發 A | 前端骨架、問卷與結果、清單／詳情、UI 狀態及易用性修正 |
| 開發 B | 官方資料整理、規則引擎、bridge 與保存、城市通建置及部署設定 |
| 內容／測試協作者 | 規則來源、文案與畫面檢視、聯繫流程複核及照顧者測試、Demo 演練 |

兩位開發者在開始時約定 Provider、GuidanceResult、ActionPlan、bridge adapter 的介面。規則與資料可以先用明確標示的測試 fixture 開發；正式 Demo 名單換成經整理的官方快照。

## 2. 開發順序與依賴

```text
S0 規格與分流確認
        ↓
S1 前端骨架＋城市通開啟測試
        ├─ S2 官方資料整理 ─┐
        ├─ S3 規則與模板 ──┼─ S4 核心畫面與資料接合
        └─ UI 靜態畫面 ───┘             ↓
                              S5 撥號與本機保存
                                        ↓
                              S6 實機／內容／使用者驗證
                                        ↓
                              S7 凍結、部署及 Demo
```

規則複核與測試招募在 S0 啟動，文件與來源紀錄在每階段同步更新。S1 即先驗證「App 能開網頁」，避免最後才處理整合問題。

| 階段 | 預估人時 | 主要產出 | 完成條件 |
| --- | --- | --- | --- |
| S0 規格與分流 | 2–3 | 範圍、規則表、驗收案例 | 團隊理解相同，未知項目有處理方式 |
| S1 專案與連通 | 2–3 | 前端骨架、服務入口、測試網址 | 至少一台實機能由城市通開啟頁面 |
| S2 資料整理 | 3–4 | 匯入腳本、資料快照、來源與異常報告 | 可重現匯入，跨區篩選所需欄位可用 |
| S3 規則與摘要 | 3–4 | 分流邏輯、聯絡摘要、待辦模板 | 各分支及未知答案都有可追溯結果 |
| S4 核心介面 | 6–8 | 五個畫面與完整導覽 | 能從問卷走到行動清單 |
| S5 撥號與保存 | 3–4 | bridge adapter、localStorage、失敗處理 | 撥號、恢復及清除在目標實機可操作 |
| S6 驗證與修正 | 4–5 | 自動化檢查、實機紀錄、使用者測試紀錄 | 重大錯誤修正，未完成驗證如實揭露 |
| S7 交付與演練 | 2–3 | 可重現版本、部署、文件及 Demo | 實機完整流程可重複展示 |
| 合計 | 25–34 | P0 技術實作與早期驗證 | 使用價值結論依實際招募與檢核結果判定 |

## 3. S0：確認規格及驗證方式

執行工作：

1. 確認正式題目、主要平台、服務名稱及既有 Flutter 建置狀態。
2. 以規格文件的 R0–R4 建立決策表，逐項記錄問題、答案、結果及官方來源。
3. 將「到府需求、首次接觸長照」定為主要 Demo 情境；已有個管員為第二條展示路徑。
4. 寫出每個畫面的主要動作，以及無符合結果時的官方諮詢路徑。
5. 開始邀請一位流程複核者、三位照顧者；未找到人時持續開發技術流程，記錄內容與使用價值尚待驗證。
6. 約定資料模型、工作分工、版本控管及 P0 功能清單。

產出：規則表、五個畫面線框、代表案例及待確認清單。能在紙上走通所有分支後進入畫面開發；服務範圍等未確認資料保守處理，不能補上推測內容。

## 4. S1：建立專案並提早打通城市通

網站位於本 repository 的 `carepass/`；Flutter 位於獨立的 TownPass repository。兩邊各自建置，網站部署至 Vercel 後，App 透過 `CAREPASS_URL` 載入 HTTPS 網址。

```text
townpass2026-starter/
├─ carepass/
│  ├─ src/
│  │  ├─ pages/
│  │  ├─ components/
│  │  ├─ domain/        # 資料模型、規則、摘要模板
│  │  ├─ adapters/      # bridge 與本機儲存
│  │  ├─ data/          # providers.json、sources.json、guidance.json
│  │  └─ styles/
│  ├─ scripts/          # 匯入與資料檢查
│  ├─ tests/
│  └─ README.md
└─ docs/
│  ├─ CAREPASS_POC_SPEC.md
│  └─ CAREPASS_POC_DEVELOPMENT_PLAN.md

TownPass/              # 獨立 repository：城市通 App、入口及 bridge
```

執行工作：

1. 建立 Vite／React／TypeScript 專案，固定套件版本與 lockfile。
2. 加入 TypeScript 檢查、production build 及核心邏輯測試指令。
3. 定義城市通色彩、文字、間距、按鈕與卡片的最小元件集合。
4. 準備 HTTPS 測試頁，驗證重新整理與直接進入路徑的行為。
5. 在 `my_service_model.dart` 加入服務 id、名稱、描述、圖示與 destinationUrl，新增圖示後依專案流程產生程式碼。
6. 在主要 Demo 手機建置 App，從「服務」進入測試頁，再返回城市通。

完成條件：實機開啟頁面、載入資產及返回操作正常。若原生建置失敗，另一位開發者持續前端與資料工作，建置問題優先排除；瀏覽器可操作只能標記為網頁成果。

## 5. S2：整理官方資料快照

執行工作：

1. 以來源 manifest 固定 dataset URL、resource id、取得時間及來源更新時間。
2. 匯入居家式 CSV，處理 Big5 解碼與必要欄位檢查。
3. 輸出 Provider 與 SourceManifest；保留電話／分機、原始服務區別、喘息及短照代碼。
4. 正規化服務行政區，處理多種分隔符號；檢核「全區」的定義。
5. 產生缺漏、未知行政區、疑似重複、電話格式及解析失敗報告。
6. 手動抽查來源列、轉換結果及畫面顯示；納入位於其他區、但服務所選行政區的例子。
7. 將有效快照納入版本，下載失敗或資料不合格時保留上一份，不在網站載入時重新抓 CSV。

完成條件：可重現匯入；名單能依已確認的服務範圍正確篩選；資料出處與日期可追溯。筆數變動是檢查訊號，不以本次 165 筆作為永遠不變的斷言。

## 6. S3：實作規則、聯絡摘要及行動計畫

執行工作：

1. 實作可單獨測試的 `evaluateGuidance(answers)`，回傳 ruleId、建議、主要行動及來源。
2. 依優先順序處理地區、需求類型、是否已有服務與是否知道個管員；不推斷法定資格。
3. 實作服務範圍篩選；原始值不明的單位不當作已確認符合。
4. 實作固定模板的 `buildContactSummary`，選填時段只加入文字，不影響名單。
5. 實作 `createActionPlan`：沒有選單位也能建立以個管員或官方諮詢為下一步的清單。
6. 將規則與模板版本寫入計畫，記錄來源及複核狀態。

完成條件：首次申請、已有個管員、找不到個管員、不清楚、其他地區與其他照顧方式均有明確輸出；相同輸入產生一致結果。完成內容複核前，模糊處使用官方入口轉介。

## 7. S4：完成五個畫面

建議實作順序：需求引導 → 下一步建議 → 行動清單 → 單位清單 → 單位詳情。先打通「問完就知道要做什麼」，再接上單位查詢。

執行工作：

1. 問卷支援返回、答案保留、條件式問題及「不清楚」。
2. 結果頁以一個優先行動呈現聯絡對象與理由，保留官方來源。
3. 行動清單顯示聯絡摘要、詢問事項、手動待辦及資料日期。
4. 接入官方名單，顯示篩選條件及固定排序；不以機構地址代替服務範圍。
5. 詳情頁提供電話、分機、地址及服務說明；無電話時仍能回到官方諮詢。
6. 加入無結果、缺漏資料、無法複製及未保存等畫面狀態。
7. 檢查窄螢幕、文字縮放、長機構名稱、讀屏標籤、返回操作及觸控區域。

完成條件：不依賴後端或 LLM，能使用真實官方快照完成一條主流程。測試 fixture 與正式來源在程式及畫面紀錄中可區別。

## 8. S5：撥號、本機保存與整合

執行工作：

1. 將網頁撥號集中封裝到 bridge adapter，使用既有 `phone_call` 能力。
2. 將號碼與分機分開顯示；不把 canLaunch 回覆當成接通成功。
3. 非 App 環境或無法啟動撥號時，提供 `tel:`／可複製文字，依實際平台驗證結果呈現。
4. 使用有 schemaVersion 的 localStorage adapter，保存單一計畫與最小必要答案。
5. 實作勾選、重開恢復、清除，以及重新產生計畫前的取代提示。
6. 處理儲存失敗、損壞資料、舊版本資料與已不在新名錄中的單位；無法恢復時提供重建清單及官方下一步。
7. 在正式候選網址的 WebView 實測關閉、重開、App 重啟及外部官方連結返回。

完成條件：目標手機上能開啟撥號並取消、手動維護待辦、重開恢復及清除；UI 清楚說明本機保存的限制。第一版不新增排程通知。

## 9. S6：驗證與修正

核心規則、服務區域篩選及儲存失敗處理適合自動化測試；靜態文案或單純顏色不另外建立與實作鏡像的測試。

| 案例 | 檢查方式 | 預期結果 |
| --- | --- | --- |
| 已使用長照且知道個管員 | 邏輯測試＋畫面操作 | 先聯絡既有個管員，能保存摘要 |
| 首次使用長照 | 邏輯測試＋內容檢核 | 官方申請路徑清楚，沒有自動通過資格的結論 |
| 狀態不清楚／找不到個管員 | 邏輯測試 | 提供確認現況的窗口及清單 |
| 其他地區／需求方式 | 邏輯測試 | 不顯示已確認適用的臺北居家名單 |
| 機構地址不在所選區但服務涵蓋該區 | 資料 fixture＋官方列抽查 | 正確列入結果 |
| 全區未確認／行政區無法解析 | 邏輯測試 | 不默認為符合；異常報告可查 |
| 無結果／電話缺漏 | 畫面操作 | 能繼續走官方諮詢與保存清單 |
| WebView bridge 不存在 | adapter 測試＋瀏覽器操作 | 顯示號碼及可行替代操作，不崩潰 |
| 撥號後取消 | 實機操作 | 待辦不自動完成 |
| 重開及 App 重啟 | 實機操作 | 依宣告的支援行為恢復計畫 |
| 儲存不可用／資料損壞 | adapter 測試 | 可閱讀、複製或重建，不誤稱保存成功 |
| 上游下載失敗 | 匯入測試 | 不覆蓋上一份有效快照 |
| 文字放大與讀屏 | 實機操作 | 核心動作可用、標籤與焦點可理解 |

完成適合本次改動的前端型別檢查、核心測試及 production build；Flutter 依變更執行分析與必要檢查，並完成實機 smoke test。至少完整驗證一個主要 Demo 平台；若宣告同時支援 iOS、Android，兩者都需實機驗收。模擬器不能作為電話行為的唯一證據。

內容與使用者驗證：

1. 請流程複核者檢查 R0–R4、名詞、服務區別解讀及聯絡摘要。
2. 邀請三位照顧者，在不提示答案的情況下完成「暫時離家，希望有人到府協助」任務。
3. 記錄耗時、卡住位置、需要解釋的詞、使用者說出的第一步，以及是否成功保存清單。
4. 以至少兩位在三分鐘內理解聯絡下一步作為本輪目標；優先修正分流誤解，再處理視覺細節。
5. 找不到目標使用者時，只交付技術驗證結果，將使用價值驗證排入下一輪。

## 10. S7：版本凍結、部署與展示

執行工作：

1. 固定候選版本、資料版本、規則版本及依賴 lockfile。
2. 檢查正式建置、HTTPS 路徑、資料與資產快取策略、重新整理及直接開啟頁面。
3. 將正式網址填入城市通入口，重裝或更新 Demo App，完整重跑主流程。
4. 準備可重現的靜態建置輸出與上一個可用版本；資料來源網站故障時仍使用版本內快照。
5. 準備備用手機及已驗證的連線方式。斷網時首次開啟網站未經實作驗證，不宣稱完整離線功能。
6. 整理原始碼、README、資料來源與取得／更新日期、套件授權、已知限制、測試紀錄及部署方式。
7. 依提供的競賽規範整理作品 AGPL-3.0 與指定授權聲明，保留既有 TownPass 授權告示；確切繳交方式與現場要求另核對。原始碼公開與外部部署屬後續交付動作，本次未執行。
8. 依實際進入階段準備約兩分鐘與約五分鐘的作品操作演練，正式時長以現場通知為準。

兩分鐘 Demo 建議：

| 時間 | 展示內容 |
| --- | --- |
| 0:00–0:15 | 說明照顧者的到府喘息需求與產品目標 |
| 0:15–0:45 | 從城市通進入，選擇服務地區與既有長照狀態 |
| 0:45–1:10 | 展示應先找誰，以及這條路徑的理由 |
| 1:10–1:35 | 查看官方單位、聯絡摘要與行動清單 |

演練及展示不實際撥出電話給 1966 或服務單位。需要測試接通時另使用團隊自行提供的測試號碼。

- 主情境：臺北市、到府需求、尚未使用長照的官方聯絡路徑；已有個管員只保留簡短分流。
- 問卷、下一步、名單／詳情可合併呈現，保留摘要與行動清單。
- 使用已檢核的官方居家資料快照；範圍未確認的資料不當作已符合。
- 以一個實機平台完成城市通開啟、撥號入口及本機保存。
- 照顧者訪談、第二平台及更多例外驗證若未完成，明確列入賽後。

## 12. 風險與刪減順序

| 風險 | 處理方式 | 是否影響對外宣稱 |
| --- | --- | --- |
| 流程無法及時完成專業複核 | 保守提供官方轉介，保留來源及待複核標記 | 只能宣稱技術原型 |
| 招募不到照顧者 | 繼續技術驗證並安排下一輪 | 不宣稱已證實降低照顧負擔 |
| 「全區」或區別文字不明 | 保留原始值、人工確認，未確認不納入已符合名單 | 說明名單涵蓋限制 |
| 來源站或跨來源下載不穩 | 採隨版本資料快照，更新時才抓取來源 | 不宣稱即時資料 |
| Flutter 建置或 WebView 行為異常 | S1 提早發現，固定可運作平台與版本 | 網頁可用不等於 App 整合完成 |
| localStorage 無法保存 | 保留畫面與複製摘要、明示尚未保存 | 不宣稱跨裝置或永久保存 |
| 工時超出 | 先簡化裝飾與動畫，再合併畫面、收斂展示分支 | 保留資料真實性、官方來源及下一步 |

地圖、定位、通知、其他服務類型與 AI 全部留在 P1，不占用競賽緩衝。競賽前若連最小主流程都尚未打通，先停止增加查詢條件，集中完成官方聯絡路徑、摘要及保存。
