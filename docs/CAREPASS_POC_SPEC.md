# 照護通 CarePass：修正版 POC 規格

版本：0.1；規劃日期：2026-11-07，Asia/Taipei。

本文件將原提案與開發評估收斂成第一版規格。CarePass 已開始依此實作，現況與執行方式見 `../carepass/README.md`；需求分流仍須經熟悉長照流程的人檢核。

## 1. 產品目標與驗證假設

一句話定位：協助臺北市家庭照顧者，在三分鐘內知道應先聯絡誰、要詢問什麼，並保存可執行的喘息服務行動清單。

主要使用者為需要暫時離家、希望有人到府協助照顧家人的家庭照顧者。第一版聚焦居家喘息需求，納入首次接觸長照、已有個管員及狀態不明三種情況。

POC 要驗證三件事：

1. 少量白話問題，能否協助使用者理解正確聯絡路徑。
2. 官方特約名錄，能否依被照顧者的服務地區整理成可詢問的單位清單。
3. 聯絡摘要、詢問事項及待辦，是否能減少使用者自行整理資訊的負擔。

三分鐘是建議的驗收目標，尚無實測結果。成功事件為使用者能說明下一步並保存清單；開啟撥號不代表已聯絡成功，也不代表服務已安排。

## 2. 修正重點

| 原提案項目 | POC 修正版 |
| --- | --- |
| 「誰能在指定時段幫忙照顧」 | 提供聯絡路徑與需求摘要；希望時段僅供詢問，不用於確認空位 |
| 涵蓋多種喘息資源 | 主流程先完成居家喘息；其他需求導向官方資訊 |
| 依行政區、地理位置找附近單位 | 依被照顧者實際服務地區與名錄的服務範圍篩選 |
| 個人化行動計畫 | 明確包含先找誰、聯絡摘要、詢問事項及手動待辦狀態 |
| 定位及通知視進度整合 | 第一版採手選行政區、撥號及本機保存；定位與排程通知列入後續 |
| 直接讀取 CSV／API | 先以整理腳本產生隨版本附帶的官方資料快照 |
| 「順利取得下一步」 | 用分流檢核、照顧者操作與實機驗收量測 |

## 3. 功能範圍

### 第一版必要功能 P0

- 城市通內的 CarePass 服務入口與 WebView，載入獨立部署的 HTTPS 網址。
- 簡短需求引導，所有狀態題都有「不清楚」選項。
- 三條聯絡路徑及各自的理由、官方出處。
- 居家喘息特約單位清單、服務範圍及詳情。
- 1966 與單位電話的撥號入口；分機獨立顯示，方便使用者接通後輸入。
- 依回答組合聯絡摘要與詢問清單。
- 單一行動計畫的本機保存、重開恢復、待辦勾選與清除。
- 資料來源、來源更新日期、取得日期及名錄限制說明。
- 無符合結果、資料缺漏、儲存失敗及無法撥號的替代操作。

### 後續功能 P1

- 其他喘息服務類型的完整引導與清單。
- 地圖、使用者主動啟用的定位及地址座標整理。
- 定時提醒，包含建立、修改、取消、權限及重啟後排程驗證。
- 自動資料更新流程、變更報告與定期內容複核。
- 跨裝置同步或多份行動計畫，待實際需求確認後評估。

### 本次範圍外

正式申請送件、案件進度串接、即時預約、空位保證、人員媒合、付款、資格或補助額度自動判定、醫療建議、雲端 LLM 與裝置端 LLM。

## 4. 問卷及分流

問卷採短步驟設計，返回上一題會保留答案。第一版不要求姓名、身分證字號、完整住址、病歷或自由輸入病況。

| 輸入 | 選項／處理方式 | 用途 |
| --- | --- | --- |
| 需要服務的地區 | 臺北市 12 行政區；其他地區；不清楚 | 明確詢問被照顧者的服務地點，非照顧者手機所在地 |
| 希望得到的協助 | 有人到家中協助；想了解其他方式；不清楚 | 到府需求進入居家名錄；其餘提供官方諮詢入口 |
| 是否已使用政府長照服務 | 是；否；不清楚 | 聯絡路徑分流 |
| 是否知道個管員的聯絡方式 | 知道；不知道；不清楚 | 在已使用長照服務時顯示 |
| 希望使用服務的時段 | 選填；明確標註僅供聯絡摘要 | 不參與名單篩選、排序或可用性推論 |

分流優先處理地區及服務需求，再處理既有長照狀態：

| 規則 | 條件 | 結果與主要行動 |
| --- | --- | --- |
| R0 | 非臺北市或地區不清楚 | 提供官方諮詢及所在地窗口入口；不套用臺北市名錄推論服務範圍 |
| R1 | 非到府需求或需求不清楚 | 提供喘息服務的白話說明與官方諮詢入口 |
| R2 | 已使用長照，且知道個管員聯絡方式 | 先整理需求，聯絡既有個管員確認服務安排；可查看名錄供討論 |
| R3 | 尚未使用長照 | 提供 1966／官方線上申請入口，說明申請、評估與照顧計畫流程 |
| R4 | 長照狀態不清楚，或已使用但找不到個管員 | 聯絡官方窗口確認現況，保存需求摘要 |

R0／R1／R3／R4 同樣可以建立行動清單；不要求先選擇服務單位。首次申請者若瀏覽名錄，須清楚看到「供預先了解，後續安排需由正式窗口確認」。

每條規則記錄 ruleId、適用條件、顯示文字、官方來源、複核日期及複核狀態。未經確認的流程細節保持官方入口轉介，不自行產生資格結論或承諾辦理時程。

## 5. 五個畫面與互動

| 畫面 | 主要內容 | 完成條件 |
| --- | --- | --- |
| 需求引導 | 白話選項、步驟進度、服務地區、選填時段 | 能返回修改，支援「不清楚」，未填選填欄也可繼續 |
| 下一步建議 | 優先聯絡對象、理由、流程說明、官方連結 | 使用者可直接建立清單；能理解為何走這條路徑 |
| 單位清單 | 符合服務範圍的居家單位、篩選條件、來源日期 | 篩選可重設，無結果仍有官方諮詢下一步 |
| 單位詳情 | 名稱、地址、服務區別、電話、分機、資料出處 | 可開啟撥號或複製號碼；缺漏欄位不顯示成錯誤資訊 |
| 我的行動清單 | 聯絡摘要、詢問事項、待辦、保存與清除 | 重開可恢復；狀態由使用者手動更新 |

聯絡摘要範例：

> 我想詢問在文山區的居家喘息服務，希望下週三下午約三小時到府協助照顧家人。目前尚未使用政府長照服務，請問應先完成哪些步驟？

摘要以固定模板與選項組合產生。使用者未提供時段時，省略時段句子。可複製文字；剪貼簿不可用時，提供可選取的文字區塊。

待辦狀態限「待處理、待回覆、已完成」，並說明為個人紀錄。撥號事件不能自動把待辦改成已完成。

## 6. 資料契約與處理

2026-11-07 的下載檢查結果：居家式 165 筆、社區式 56 筆、住宿式 65 筆、巷弄式 26 筆，合計 312 筆原始列，尚未去重。四份名錄採 Big5 編碼，欄位有所差異。這是來源快照的觀察結果，不是未來匯入時必須符合的固定筆數。

第一版先整理居家式名錄。其他三份列入來源清單，供後續擴充。資料沒有經緯度、可服務時段或即時空位；機構地址、行政區域代碼與實際服務區別必須分開處理。[官方資料集](https://data.taipei/dataset/detail?id=959c34b2-9698-4d99-8987-d389efe18c04)

「如何申請長照服務」資料目前為三筆申請管道資訊，不能直接當作完整規則引擎。分流文案另依官方申請流程整理。[申請管道資料集](https://data.taipei/dataset/detail?id=e1e24ba4-3293-4d38-a915-ac65d1365fb2)

建議資料模型：

| 模型 | 必要欄位 |
| --- | --- |
| Provider | id、名稱、serviceType、原始服務區別、正規化服務行政區、範圍確認狀態、機構地址、電話、分機、原始喘息／短照代碼、sourceResourceId、sourceRowId |
| SourceManifest | datasetUrl、resourceUrl、sourceUpdatedAt、fetchedAt、資料版本、檔案雜湊、原始／輸出筆數、清理異常 |
| GuidanceRule | ruleId、條件、下一步文字、來源連結、reviewedAt、reviewStatus |
| ActionPlan | schemaVersion、ruleVersion、dataVersion、選項答案、選用的 providerId、必要聯絡資訊快照、摘要、待辦狀態、updatedAt |

清理與篩選規則：

1. 將 Big5 解碼成 UTF-8，驗證必要欄位，移除首尾空白並保留原始內容供追溯。
2. 正規化服務區別中的頓號、逗號、「及」等分隔方式。未知值記入異常報告，不能默認為全區服務。
3. 「全區」的指涉範圍列入人工檢核。未確認前不宣稱涵蓋臺北市所有行政區，也不把該值當作已確認的全區命中。
4. 依已確認的服務範圍篩選，不以機構地址所在區排除跨區服務單位。
5. 喘息與短照欄位分開保留；白話說明與代碼對應需複核，不能混成同一種服務。
6. 機構識別避免只用每份 CSV 都會重複的序號。保留 resourceId 與來源列資訊；疑似重複以名稱、地址及電話比對後人工確認。
7. 名單以固定、可重現的順序顯示，例如機構名稱；不加上「最適合」「最快」或距離推薦分數。
8. 缺電話、服務範圍不明及無法解析的紀錄列為待檢查，不把缺漏內容編造補齊。

建議更新方式為比賽期間手動執行匯入、檢查報告後重新建置。下載失敗、空檔、必要欄位變動或無法解析時，更新作業失敗並保留上一份有效快照，不覆蓋為空名單。上線試用後指定維護人，先採每週檢查及流程變動時複核，再評估自動化。

前端同時顯示來源更新日期與取得日期。官方目前標示名錄不定期更新，不能將本日下載描述成本日完成內容更新。

## 7. 技術架構與城市通整合

```text
開發／更新時：官方 CSV → 匯入與檢查腳本 → providers.json + sources.json

使用時：城市通 Flutter App
                  ↓ WebView（載入 Vercel HTTPS 網址）
            CarePass React + TypeScript
                  ├─ 本地規則與官方資料快照
                  ├─ 問卷、結果與行動清單
                  ├─ WebView localStorage
                  └─ 城市通 bridge：phone_call
```

實作調整：Flutter App 與網站分屬獨立 repository。網站由 `carepass/vercel.json` 設定獨立部署至 Vercel；App 必須透過 `CAREPASS_URL` 指定實際 HTTPS 網址，沒有內建網頁備援。下方 `TownPass/` 路徑代表獨立的 App repository。

前端採 Vite、React、TypeScript 與少量 CSS design tokens；避免第一版同時導入多套 UI 或狀態管理工具。靜態網站預計部署至 Firebase Hosting，既有可用的 HTTPS 靜態代管也可沿用。使用端不需查詢自建後端或資料庫。

城市通既有整合位置：

- 服務入口：`TownPass/lib/page/city_service/model/my_service_model.dart`。
- 圖示：`TownPass/assets/svg/`，新增後依專案流程重新產生資產程式碼。
- bridge：`TownPass/lib/util/web_message_handler/tp_web_message_listener.dart` 與 `tp_web_message_handler.dart`。
- 現有 `phone_call` 可開啟撥號；回覆代表是否能啟動，不是電話接通或聯絡完成。
- 現有 `notify` 使用立即顯示通知方法，第一版不將其當作排程提醒。

網頁封裝 bridge adapter，檢查 bridge 是否存在並處理無法使用的情況。一般瀏覽器提供 `tel:`／複製電話替代操作，未驗證前不宣稱各平台行為一致。官方外連須保留回到 CarePass 的操作路徑。

第一版只保存一份行動計畫，預設寫入該網站來源的 localStorage。須在目標 WebView 實測關閉、重開及 App 重啟的行為；清除 App 資料、換裝置或變更來源網域後不保證恢復。寫入失敗時仍可看清單及複製摘要，畫面明確標示尚未保存。

資料快照可降低對上游資料站即時連線的依賴，不能因此宣稱網站首次開啟可離線使用。完整離線載入另列後續需求。

## 8. 文案與介面原則

- 沿用城市通 UI kit 的色彩與元件語言，內文先以 16–18 CSS px 為設計起點，並實測文字縮放。
- 每個畫面只有清楚的主要行動；觸控區域目標至少 48 × 48 CSS px。
- 文字放大 200% 後，核心內容及按鈕仍可使用；驗證讀屏標籤、焦點順序與錯誤提示。
- 「個管員」旁提供白話解釋，不要求使用者先懂 GA／SC 等代碼。
- 單位詳情明示名錄不代表即時可安排；希望時段須聯絡確認。
- 1966 服務時間依官方頁面維護，非服務時段仍可保存清單並查看官方線上入口。
- 修改問卷並重新產生清單時，先明確提示會取代現有計畫，避免默默清除使用者紀錄。

## 9. 驗收與 POC 判定

| 面向 | 通過條件 |
| --- | --- |
| 規則正確性 | 所有分流都有來源、預期結果及案例；至少一位熟悉長照流程者完成檢核，未複核項目有明確標記 |
| 資料正確性 | 匯入有筆數與異常報告；已確認服務範圍的篩選案例通過，包含機構跨區服務 |
| 可操作性 | 城市通進入、完成問卷、看結果、選用單位、開啟撥號及保存清單可完成 |
| 保存行為 | 在宣告支援的實機與來源網域，重開可恢復；儲存不可用時有明確提示 |
| 例外狀況 | 無結果、無電話、非臺北市、不清楚答案及 bridge 不存在時，均有下一步 |
| 使用者理解 | 目標邀請三位照顧者，至少兩位能在三分鐘內說出先找誰、要問什麼，並保存清單 |
| 易用性 | 完成 200% 文字縮放、讀屏及主要觸控區域的實機檢查 |
| 可接手 | 新環境依文件可建置；資料更新、來源、授權與已知限制可查閱 |

只有團隊測試完成時，標記為「技術流程已驗證」。照顧者或流程專業檢核尚未完成時，保留「使用價值／流程內容待驗證」，不能用團隊成員代測結果冒充真實使用者驗證。上述小樣本結果作為下一輪改進依據，不作普遍成效推論。
